# P12 — Lua-side custom paint regions

**Status:** Phase A landed **Drafted:** 2026-05-07 **Last updated:** 2026-05-08

P12 closes the last surface gap from the P11 Lua-API audit: option G —
custom paint regions accessible from Lua. The infrastructure already
exists (`smelt-term::render_with_paints` walks `LayoutTree::Leaf(PaintId)`
nodes and dispatches to a host-supplied paint function); P12 wires that
dispatch to Lua-registered painters.

The driving signal: a 1500-line widget like a snake game, a sparkline
panel, or a half-block treemap doesn't belong in the Buffer model
(lines + highlight extmarks). Its content is *cells*, not *text*. The
Buffer pipeline (text shaping → highlight projection → cell write) is
the wrong abstraction; what these widgets want is a `GridSlice` they
can write directly.

tcloc demonstrates the pattern from Rust today (`render_legend` /
`render_treemap` write straight into `GridSlice`); P12 is plumbing the
same dispatch from Lua.

## Decisions made

- **Paint dispatch is per-PaintId**, registered on `Ui` (or the host's
  Surface for non-editor consumers). The renderer's
  `render_with_paints` already walks paint ids; P12 adds a Lua-side
  registry keyed by `PaintId`, stored on the editor `Ui`'s callback
  table, that wraps the painter as a `Callback::Lua(handle)`.
- **`GridSlice` exposed as Lua userdata**, not a copy-and-commit
  buffer. The painter writes directly into the renderer's grid for the
  leaf's rect — same semantics as a Rust-side painter. No allocation
  per frame.
- **Bulk primitives by default; per-cell as escape hatch.** API: `set`,
  `put_str`, `fill_rect`, `width`, `height`. The first three cover 99%
  of widgets at one FFI call per drawn shape, not per cell. A snake
  game with 30-cell body and 1 food becomes ~3 calls/frame regardless
  of grid size.
- **No frame-buffer upload primitive in Phase A.** `slice:blit(fb)`
  is the right shape if FFI per-shape becomes the bottleneck, but
  profiling-driven. Snake at 60fps is fine on the direct path; charts
  and sparklines run at update-rate, not framerate. Add only if a real
  widget shows the cost.
- **TLS+unsafe for slice lifetime, not `mlua::Lua::scope`.** The draft
  spec described `Lua::scope` for the `GridSlice<'_>` lifetime hazard.
  Landed with TLS+RAII guard (`SliceGuard`) instead: `with_slice` is
  the only entry point, the guard clears the pointer on drop (panic-safe),
  and `slice methods` error cleanly with `"smelt.paint: slice not in scope"`
  if called outside a paint callback. Prerequisite to switch: a real
  non-trivial workload showing scope allocation cost (60 Hz dashboards),
  and a clear readback-method list (slice:get_cell impacts lifetime shape
  under scope). See post-Phase-A notes below.
- **`PaintRegistry` on `TuiApp`, not on `Ui`.** Keeps smelt-edit and
  smelt-term untouched; the registry lives in `crates/tui/src/lua/paint.rs`
  (`PAINT_ID_BASE = 1<<32`, `LeafKind` enum for dispatch disambiguation).
  `Surface::render` (smelt-term) takes a `PaintDispatch` closure so
  non-editor consumers supply their own dispatch without a registry.
- **Parsers extracted from `ui_ops.rs` into `lua/parse.rs`.** Post-Phase-A
  tightening (`68f13a15`): 14 parsers (`style`, `color`, `color_*`, `constraint*`,
  `border*`, `corner`, `title`) moved to a dedicated `lua/parse.rs` with unit
  tests. `ui_ops.rs` shrank from ~1040 to ~647 lines. `paint.rs` uses
  `parse::style` directly (no re-export needed).
- **`LeafKind` enum disambiguates WinId vs PaintId in overlay `win` field.**
  `crates/tui/src/app/TuiApp::resolve_leaf_id(raw: u64) -> Option<LeafKind>`
  replaces the inline dual-namespace check in `open_overlay`. Debug-asserts
  enforce the `PAINT_ID_BASE` partition at both allocator and resolver sites.
- **Snake demo in `examples/`, not `plugins/`.** Early dogfood; not
  autoloaded. `runtime/lua/smelt/examples/snake.lua` (~480 lines) drives
  two paint regions (playfield + perf panel), timer-based animation, and
  input via `smelt.win.set_keymap`. Space resets; snug overlay sizing.
- **Skipped:** off-screen composition surfaces, GPU-style retained
  scenes, sub-cell shading helpers (callers compose Unicode block
  glyphs themselves). All viable later if a widget demands them; none
  enable the snake-game-class motivation.

## Architecture

Today, `smelt-edit::Ui::render` walks the active layout tree and
overlays. For every `LayoutTree::Leaf(PaintId)`, it consults a
dispatcher: WinId-range ids route to `Window::render` (the Buffer
painter); other ids go to a host-supplied paint function. The renderer
itself ascribes no semantics to the id — that's why tcloc, with no
windows at all, can use the same primitive.

P12 adds a third dispatcher branch: ids registered with `smelt.paint`
route to a Lua callback. The Lua callback receives a `GridSlice`
userdata sized to the leaf's resolved rect, runs to completion, and
returns nothing (no result needed — writes happened in place).

```
LayoutTree::Leaf(paint_id)
        │
        ▼
  paint dispatcher
        │
        ├── PaintId in WinId range  →  Window::render(slice, theme, …)
        ├── Lua-registered          →  Lua: paint_fn(slice)            ← P12
        └── otherwise                →  host's custom painter
```

The paint id allocation lives on `TuiApp`'s `PaintRegistry` in tui
(keeping smelt-edit/smelt-term untouched). `Surface::register_paint`
mirrors the shape for non-editor consumers.

## Phase A — paint registry + GridSlice userdata ✅ (landed `2fbbf7a9` + `68f13a15`)

Self-contained. A Lua plugin can now paint a snake game or a sparkline
directly into a leaf rect.

### A.1 — paint id allocator ✅

**Landed:** `PaintRegistry` in `crates/tui/src/lua/paint.rs` allocates
ids ≥ `PAINT_ID_BASE` (= `1 << 32`). `TuiApp::paint_registry` owns the
registry; `TuiApp::render_with_paints` dispatches via `resolve_leaf_id`.
`Surface::register_paint` in `crates/term/src/surface.rs` mirrors the
shape for non-editor consumers.

**Deviation from plan:** allocator lives on `TuiApp` (in tui) rather
than on `Ui` (in smelt-edit). Avoids touching smelt-edit/smelt-term for
a tui-specific Lua concern. `Surface` (smelt-term) exposes a `render`
method taking a `PaintDispatch` closure — callers supply the dispatch
logic rather than registering into a table on Surface itself.

### A.2 — `GridSlice` Lua userdata ✅

**Landed:** `crates/tui/src/lua/paint.rs` exports the userdata. Methods:
`set` / `put_str` / `fill_rect` / `width` / `height`. Lifetime hazard
handled via TLS `SliceGuard` (RAII, panic-safe) rather than `Lua::scope`
(see Decisions).

`crates/tui/src/lua/api/paint.rs` is a thin 50-line dispatcher that
calls into the registry; the userdata + methods + guard live in
`paint.rs`.

### A.3 — `smelt.paint` Lua module ✅

**Landed:** `runtime/lua/smelt/paint.lua` exposes
`smelt.paint.register(fn) -> paint_id` / `smelt.paint.unregister(id)`.
Hoisted to `smelt.paint` in `init.lua`.

### A.4 — overlay item accepts paint id ✅

**Landed:** `TuiApp::resolve_leaf_id(raw: u64) -> Option<LeafKind>`
replaces the inline dual-namespace check in `open_overlay`. Returns
`LeafKind::Window(WinId)` or `LeafKind::Paint(PaintId)`. Debug-asserts
enforce the `PAINT_ID_BASE` partition.

### Post-Phase-A tightening ✅ (`68f13a15`)

Three follow-up items landed in one commit after Phase A:

1. **Parser extraction.** 14 parsers moved from `ui_ops.rs` into a new
   `lua/parse.rs` with unit tests (`style`, `color`, `color_*`,
   `constraint*`, `border*`, `corner`, `title`). `ui_ops.rs` shrank from
   ~1040 to ~647 lines; `paint.rs` references `parse::style` directly.
2. **`LeafKind` + `resolve_leaf_id`.** Replaces the inline dual-namespace
   check in `open_overlay` with one typed helper.
3. **Namespace partition docs + asserts.** `PAINT_ID_BASE` is `pub(crate)`
   with an explicit contract docblock; `PaintRegistry::register`
   debug-asserts the allocator stays in the paint half; `resolve_leaf_id`
   debug-asserts WinIds never cross into paint range.

### Snake demo ✅ (`765dcc1f` … `57911b04`)

`runtime/lua/smelt/examples/snake.lua` (~480 lines) is the dogfood widget.
Two paint regions (playfield + perf panel); timer-driven animation;
`smelt.win.set_keymap` for input; space to reset; snug overlay sizing.
Lives in `examples/` (not autoloaded), not `plugins/`.

## Phase B — example plugin + storybook (one PR, ~150 LOC)

Stress-tests the API with a real-shape widget. Optional in the sense
that it doesn't gate further work, but it's the dogfood pass that
catches surface defects.

### B.1 — sparkline plugin

**What:** `runtime/lua/smelt/plugins/sparkline.lua` — reads a sample
buffer (last N values), renders a half-block sparkline into a paint
region. Exposes `:Sparkline open` / `:Sparkline push <n>`. Pure Lua,
~80 lines.

**Why this widget:** half-block rendering (`▁▂▃▄▅▆▇█`) hits sub-cell
expression that's awkward in Buffer (one cell = one glyph + style; no
way to express "this cell is 5/8 filled" except via the glyph itself,
which `put_str` handles fine). Validates the slice API on a plausible
real-world shape.

**Files:**

- `runtime/lua/smelt/plugins/sparkline.lua` (new).
- Wire-up in `runtime/lua/smelt/init.lua`.

**Done when:** `:Sparkline open` overlays a 40×8 panel, `:Sparkline
push 0.5` advances the series, the sparkline updates without flicker.

### B.2 — storybook story

**What:** add a paint-region story to the storybook tests so the
renderer-level path stays covered. Story: a 20×10 paint region writes
a checkerboard via `fill_rect` calls; snapshot test asserts the grid.

**Files:**

- `crates/tui/tests/storybook/stories/paint.rs` (new).
- `crates/tui/tests/storybook/snapshots/`: generated snapshot.

**Done when:** the storybook run produces a stable snapshot for the
paint region; story renders identically across runs.

## Phase C — frame-buffer escape hatch (deferred; gated on profiling)

Only worth building if a real widget shows that per-shape FFI is the
bottleneck. The shape:

```lua
local fb = smelt.framebuf.new(w, h)  -- userdata, owns a Vec<Cell>
fb:set(row, col, char, style)         -- pure Lua → C cell write
slice:blit(fb, dst_row, dst_col)      -- one FFI: bulk memcpy
```

Skip until a widget needs it.

## Out of scope

- Off-screen composition (render to a texture, blend, etc.). Adds
  retained-mode complexity for no current widget.
- GPU acceleration / dirty rects within a paint region. Compositor
  already does cell-level diffing on the final grid; widget-level
  dirty tracking belongs in Lua if a plugin wants it.
- Mouse hit-testing on paint regions. Already supported via
  `HitTarget<P>` from P11; P12 doesn't change this — paint regions
  participate in hit-testing as opaque rects, and Lua receives mouse
  events via the existing keymap/event path.
